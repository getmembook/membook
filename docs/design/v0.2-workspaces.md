# v0.2 — Multi-repo workspaces

**Status:** built, through step 7 of §14 (July 2026) — the squash-merge blob
hedge stays deferred per §11's measurement, and §15's open questions resolved
along their leans: shared manifests are docs-only, verification never fetches,
and workspace recall reads members' repo stores only, never their user
stores. The unrehearsed real-workspace acceptance run is logged in
`docs/dogfood.md`.

Written against v0.1.0-alpha (spec 101 / core 198 / mcp 21 / cli 33 tests;
three seams filled; four packages published).

One sentence: federate verification and recall across the git checkouts a
machine already has, using the anchor machinery v0.1 already built — no
server, no sync, no new storage model.

---

## 1. Why this is nearly free

Three v0.1 decisions, made for other reasons, compose into multi-repo support:

- **The anchor `kind` discriminator is always serialized** — ratified in the
  first spec session precisely so new anchor kinds would be additive. A
  cross-repo anchor is the first beneficiary.
- **Files are the truth**, and each repo's book is committed in that repo — so
  there is no central store to design, no merge protocol, no sync. Canonical
  state stays where it is.
- **The verify pass is already a pure function of `(anchor, checkout)`.** It
  diffs an anchor's last-verified commit against HEAD in a working tree.
  Nothing in it assumes that tree is the current repo; it was simply never
  handed a different one.

What v2's org-graph server imagines as infrastructure, a workspace prototypes
as federation over local checkouts, with `git pull` as the propagation medium.
This version exists to generate the evidence — do cross-repo anchors get used,
how often do they catch drift — that decides whether the server is worth
building.

## 2. Goals and non-goals

**Goals.** Cross-repo anchors verified with the existing machinery;
contract-watch-lite; federated recall with visible provenance; a home for
`scope: user`; all deterministic, honest about what it cannot see, and covered
by the fixture harness.

**Non-goals, stated as a fence.** No sync service or server. No RBAC — a local
checkout is its own access control; you can read what you can clone. No
auto-discovered dependency edges from lockfiles or manifests: declared-only,
because discovery is real v2 graph work. No cross-machine anything. No changes
to how books are committed.

If a task seems to require any of these, it is out of scope and goes to the v2
backlog instead.

## 3. The workspace manifest

A resolution table, not a database. Default `~/.membook/workspace.yaml`;
optionally committed in a meta-repo for teams wanting a shared definition (same
format; `--workspace <path>`).

```yaml
workspace: stag-main
members:
  payments-service:
    path: ~/dev/payments
    remote: git@github.com:acme/payments-service.git # identity tiebreaker, optional
  platform-gateway:
    path: ~/dev/gateway
```

Memories reference repos by **stable member name**, never by path — paths are
machine-specific; names travel in committed files.

Resolution failures are per-member and non-fatal: an absent member yields
`unresolvable` outcomes (§5), never an aborted pass. The manifest is validated
by a Zod schema in `@membook/spec` — it is standard-surface, since committed
memories reference the names it defines.

### Identity checking — ruled 2026-07-24

`remote` is compared **after normalising to canonical host/path**: the SSH and
HTTPS forms of a repository are the same identity, and a resolver that treats
them as different would reject correct workspaces. Normalise once, properly, in
the resolver.

**No `origin` at all is not a mismatch.** A local-only repo is legitimate:
resolve by path and report _identity unconfirmed_ in `status`. The loud error
stays reserved for the genuinely dangerous case — a remote that exists and
**disagrees**, which is a wrong-checkout-verification factory.

## 4. The `xgit` anchor kind

```yaml
anchors:
  - kind: xgit
    repo: platform-gateway # manifest member name
    path: config/limits.yaml
    symbol: rateLimits # optional, as today
    commit: 8c1f0a2 # last verified against, in THAT repo's history
```

Verification resolves `repo` through the manifest, then runs the **unchanged**
verify pass inside that checkout: same diff-against-last-verified, same
`log --follow` rename tracking, same transitions, same invariants — staleness
not cleared by absence of change, anchor commits advancing only on success. No
new verification logic; the pass gains a working-tree parameter and a resolver
in front of it.

`kind: git` anchors are untouched and continue to mean "this repo".

## 5. The third epistemic state: `unresolvable`

When a member repo is absent or fails identity check on this machine, its
anchors' outcome is `unresolvable` — **not** stale (nothing is known to have
changed), **not** verified (nothing was checked).

Per the lies-by-aggregation convention, this may not be folded into either
neighbour anywhere. `status` reports it on its own line with the member name
and reason. The book excludes unresolvable-anchored memories the way it
excludes stale, with the header reporting the two counts **separately**:

> N further memories could not be checked on this machine because the
> repositories they describe are not present.

Telemetry records `outcome: "unresolvable"` with the member attributed. Status
shows `(unresolvable: platform-gateway not in workspace)` — plain, like
`(unverified)`. No warning marker: a missing checkout is not a health
departure of the memory.

**Honest caveat the docs must state.** Workspace verification is always against
the checkouts this machine can see. A sibling checkout behind its remote
verifies against yesterday's reality — consistent with the tool's claim ("last
proven against `<commit>`"), but worth surfacing. `status --workspace` notes
when a member's local HEAD is behind its upstream
(`git rev-list --count HEAD..@{upstream}`, cheap, no fetch), phrased as
information rather than alarm.

## 6. Contract-watch lite

No new component — a usage pattern the docs and fixtures must demonstrate,
because it is the v2 flagship running on v0.2 primitives.

A memory in the consumer repo anchors via `xgit` to the producer's schema or
config file. The producer merges a change; the consumer developer `git pull`s
the producer checkout (which they do anyway); `membook verify --workspace`
flips the consumer memory stale **before** an agent writes code against the old
shape.

This is the signature demo of v0.2 and, like v0.1's, must exist as an automated
test — including the rename case in the producer repo.

## 7. Federated recall; sovereign books

MCP server and CLI gain `--workspace`. In workspace mode `recall` fans out
across member stores, merges ranked results, and serves every cross-repo result
with provenance visible in the payload: `[gotcha · from platform-gateway]`. An
agent must be able to distinguish local knowledge from a neighbour's testimony
— the recall-side sibling of honest attribution in telemetry.

Relevance still gates. A small cross-repo modifier (local outranks
equally-relevant remote) is applied and, like all modulation, cannot rescue a
floor failure.

The small-corpus BM25 lessons — term-coverage scaling, degenerate IDF — were
learned at single-repo scale. Assume they need re-checking when corpora merge:
add a federated-precision test alongside the existing gating invariant.

**Books stay sovereign.** Each repo's `MEMBOOK.md` is generated only from its
own store, because it is committed in that repo and must not go stale against
repos it cannot see. The session boot path (MCP `session_digest`, not the
committed file) may append a live, never-committed _workspace context_ section:
cross-repo memories from other members whose `xgit` anchors point into the
current repo — what the neighbours know about here. Same cap discipline,
counted separately in the book telemetry event.

## 8. `scope: user` — ruled 2026-07-24

User-scope memories live in `~/.membook/store/`, are included in recall in every
session, and never enter any committed book. `remember --scope user` writes them
(`origin: authored, author: human`).

**The ruling: discriminate by scope, and forbid anchors on user memories.**

Design review found this collided with a ratified invariant — the schema
requires at least one anchor, and a preference like _"I prefer explicit return
types"_ has no file to point at. It cannot borrow one either: an anchor into a
local checkout would make the memory verifiable only on this machine, the
opposite of following the human.

The invariant survives by understanding why it exists. **An anchor is what makes
a memory a checkable claim about the world.** A user preference is not a claim
about the world — it is testimony about the human, and verification is a
_category error_ against it, not a pending obligation.

So `scope` becomes a discriminated union, exactly as `origin` and `author` did:

| scope          | anchors                | verification vocabulary                       |
| -------------- | ---------------------- | --------------------------------------------- |
| `repo`, `team` | **required**, `min(1)` | full lifecycle, unchanged                     |
| `user`         | **forbidden**          | `status` and `verified` absent from the shape |

Anchors are forbidden rather than optional: if you have a file to point at, it
is not a preference — it is repo knowledge wearing the wrong scope.

The verification fields are **absent from the shape**, not perpetually
`unverified`. A memory that can never be verified must not carry a field
implying a check is pending. Presence-is-meaningful cuts both ways.

Books and verify ignore user memories by construction. Recall serves them
plainly. _The anchor is the product_ stands — for the species of memory it was
always about.

## 9. Spec changes

One anchor kind (`xgit`), one verify outcome (`unresolvable`), one manifest
schema, the `scope` discrimination (§8), and the `memfile` version tick that
`xgit` forces.

Golden fixtures: an `xgit`-anchored memory, an unresolvable outcome in
serialized form, a manifest file, a user-scope memory.

Nothing else in the wire schema moves. The provenance model, verify invariants,
book determinism rules and serialization rules are untouched — any temptation to
"improve" them while in the files is out of scope by default and needs a flagged
ruling.

### Versioning is a workstream, and it lands first — ruled 2026-07-24

Design review found the tick understated. `memfile` is a `z.literal`, so
bumping it to `2` does not merely make v1 readers reject v2 files — it makes
**our own v2 reader reject every existing v1 file**, quarantining every memory
in every repo on upgrade.

The shape:

- The spec package holds **explicit versioned schemas** (`memfileV1`,
  `memfileV2`), with parse dispatching on the field.
- **Read tolerance for all versions ≤ current, forever.**
- **Writes always emit the current version.**
- **No silent upgrade-on-touch.** Files are truth and committed, so a version
  migration must be a _reviewable diff, not a side effect_: a `membook migrate`
  command rewrites the store in one explicit commit a human can read.
- Mixed-version repos are **legal on read**; `status` reports the count;
  `migrate` closes it.
- Golden fixtures for both versions, **including a v1 file parsing correctly
  under the v2 package** — that test is the promise external implementers will
  rely on.

Sequencing correction adopted: **version machinery is step zero**, before
`xgit` forces it in anger.

## 10. Read-only fan-out — ruled 2026-07-24

Design review found "each opened read-only" impossible as written: `recall`
queries `memories_fts` and therefore needs the SQLite index, which a neighbour
who has never run Membook does not have.

**Hard rule: Membook never writes inside a checkout it did not init** — not an
index, not a byte. Polluting a neighbour's tree is both rude and a
false-comfort trap.

The resolution is _not_ a file-scan fallback. Two retrieval implementations
would have to be kept honest against each other, a consistency burden against
our own precision invariants.

It is remembering what the index **is**: a disposable derived cache — and caches
live in cache directories.

Neighbour indexes build in `~/.membook/workspace-cache/<member>/`, keyed by
member name and indexed HEAD, rebuilt when the member's HEAD moves. Same index
code, same retrieval path, different location. Their tree is untouched, and
"read-only" becomes literally true rather than load-bearing prose.

First federated recall against a large neighbour pays an index build —
acceptable, and reportable (`indexing platform-gateway…`). Incremental later if
the fortnight says it hurts.

## 11. Squash-merge — measure first, hedge recorded 2026-07-24

**Measured 2026-07-25 — hedge deferred.** Eleven repos, ~700 commits: squash
is ~1% of history in the target workspace (8 commits, confined to the two big
client repos); everything else is direct commits or merge-commit PRs, both of
which preserve the SHAs anchors point at. The only squash-heavy repo in the
sample is membook itself (33%) — GitHub-flow OSS style, which is exactly the
audience single-repo Membook already serves and where the same-day experience
of three squash-orphaned branches came from. So: no blob-hash hedge in the
v0.2 federation work; reopen this if cross-repo anchoring is pointed at
squash-flow repos.

Design review raised the risk, and it is the one most likely to decide whether
§6 works at all.

History rewriting orphans anchors — observed in v0.1 when a force-push left
`68eed03` dangling, surviving only because the object had not been gc'd.
In-repo, you control history hygiene. **Cross-repo, you do not.** A producer
that squash-merges destroys every commit its consumers anchored to, on every
merge. `unknown-base` could become the _common_ outcome rather than the
exception, and contract-watch-lite would collapse into permanent
`unresolvable`.

**Measure before building.** Check the merge style of every producer repo in the
Stag workspace during the fortnight. Free to do, expensive to discover after
§6 is built.

**The contingent hedge, if squash proves common — and in most orgs it is.**
`xgit` anchors carry the **blob hash** of the anchored file alongside the
commit (`commit` + `blob`):

- When the commit survives → full diff semantics, exactly as today.
- When history rewriting orphans it → compare the stored blob hash against the
  file's blob at HEAD. **Changed-or-unchanged is still answerable without
  history**, honestly degraded: rename tracking dies with `--follow`, so
  missing-file-plus-no-history reports as _unknown_, not _gone_.

That keeps contract-watch-lite alive in squash-world at reduced fidelity rather
than collapsing. **Do not build it preemptively** — it is written down so the
measurement has a decision waiting on each branch.

## 12. Telemetry

`verify` events gain optional `member` attribution on per-anchor outcomes;
`recall` gains `served_remote` and per-member counts; `book` gains
`excluded_unresolvable`.

The grounded-restore work applies unchanged: a cross-repo restore must quote
evidence from the member's file **at its HEAD**, mechanically checked in that
checkout.

## 13. Test plan

The fixture harness grows a `workspace()` helper spawning N temp repos plus a
manifest pointing at them. Each asserted end-to-end:

- Cross-repo drift (contract-watch-lite, §6)
- Cross-repo rename via `--follow`
- Member absent → `unresolvable` → book exclusion with honest header
- Member present but wrong remote → loud resolution error
- Member with no `origin` → resolves, reports identity unconfirmed
- Federated recall provenance and precision
- A v1 memory parsing correctly under the v2 package (§9)
- A user-scope memory rejected if it carries an anchor (§8)
- Determinism — the same workspace state yields byte-identical
  `status --workspace` output and books regardless of member iteration order
  (sort by member name)

Per the injection-blindness convention: **at least one test drives the real CLI
binary against a real multi-repo workspace on disk.**

## 14. Sequencing and acceptance

Build after the fortnight, informed by its telemetry.

0. **Version machinery** — versioned schemas, read tolerance, `membook migrate`
1. Manifest + resolver, with normalised identity check
2. `xgit` in spec + fixtures
3. Verify pass working-tree parameter + `unresolvable`
4. `scope` discrimination and the user store
5. CLI/MCP `--workspace`
6. Federated recall over the workspace cache
7. Workspace-context boot section
8. Docs

**Acceptance**, mirroring v0.1's ethic: the two-repo contract-watch demo runs as
an automated test _and_ unrehearsed on the real Stag workspace; `unresolvable`
never masquerades as stale or verified anywhere; a fresh `--workspace` run on a
machine missing a member degrades honestly rather than failing; all existing
tests untouched and green.

## 15. Open questions

Flag before build, not during.

- Shared-manifest-in-meta-repo in v0.2, or docs-only? _Lean: docs-only; the
  format already permits it._
- Should `xgit` verification auto-`git fetch` members? _Lean: never — network
  actions on verify violate least surprise. Report behind-ness instead._
- Should workspace `recall` include members' user-scope stores? _Lean: no; user
  scope is the human's, not the workspace's._

---

The propagation medium is `git pull`. The resolution table is the only new
state. Everything else is the v0.1 machinery, handed a second working tree.
